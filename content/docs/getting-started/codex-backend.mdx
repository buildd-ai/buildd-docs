# Codex Backend

The Codex backend runs a task through OpenAI's Codex agent instead of Claude.
Set `backend: codex` on a task, a role or the workspace. It runs on your
**ChatGPT plan** or on an **OpenAI API key**.

## Setup

| Option | How |
|---|---|
| **ChatGPT plan, on the runner** (recommended) | On the runner machine, run `codex login` (or `codex login --device-auth` with no browser). Then set `CODEX_HOME=$HOME/.codex` in the runner's environment so it finds the `auth.json` |
| **OpenAI API key** | In **Settings → Connections → Runners**, paste the key into the OpenAI API key card. You pay per token. You can also set `OPENAI_API_KEY` on the runner |
| **Your gateway** | A team agent model endpoint that speaks the OpenAI API (a LiteLLM gateway or OpenRouter) also serves Codex tasks. See [How Buildd Runs AI](/docs/concepts/how-buildd-runs-ai) |

The ChatGPT seat stays on the machine that logged in, like a Claude seat.

## Stored ChatGPT credentials (being removed)

<Callout type="warn">
  The Codex card in **Settings → Connections → Runners** still lets you sign in
  with a device code or paste an `auth.json`, and buildd delivers that
  credential to runners. Server-stored Codex credentials are being removed. Use
  a login on the runner instead.
</Callout>

While it lasts, a stored credential covers the whole team by default, and you
can narrow it to one workspace. Buildd refreshes the tokens before they expire. If a refresh fails, the
card shows **Expired**. Use **Refresh now**, **Re-auth via device login** or
**Paste auth.json** to reconnect, and **Verify** to check it against OpenAI.
**Revoke** deletes the stored tokens. Codex tasks already running finish on the
tokens they received at claim time.

## Security

Buildd encrypts tokens at rest with AES-256-GCM, the same as every other secret,
and never logs them. On the runner, the `auth.json` lives in a per-worker
`CODEX_HOME` (`mode 0700`, file `mode 0600`) that the runner removes when the
worker is torn down.

## Concurrent Execution

Codex tasks are **automatically serialized**: only one Codex task runs at a time per workspace. Buildd enforces this at claim time, with the runner as a backstop. No configuration needed.

The limit exists because ChatGPT plans have a **5-hour rolling usage window**. Running multiple tasks in parallel would exhaust the window faster without completing more work. Serializing tasks keeps throughput predictable and avoids mid-task quota failures.

If multiple Codex tasks are pending, they queue behind the active one and start as soon as it finishes.

## Sandbox Modes

The Codex backend applies a sandbox policy based on task type:

| Task type | Default sandbox | File access |
|-----------|-----------------|-------------|
| Research / analysis | `read-only` | Can read files, cannot write or run commands |
| Engineering / code | `workspace-write` | Can read and write within the workspace directory |

Buildd picks the sandbox from the task's `kind`: `research`, `analysis` and `observation` get `read-only`. Override it with `context.sandboxMode` on the task.

Read-only mode is appropriate for tasks that only need to inspect the codebase or external data. Workspace-write mode is required for tasks that modify files, run builds, or apply patches.
