# Runner Setup

A runner is the process that does the work. It runs on your machine, a build box
or a remote workspace, claims tasks from buildd.dev, runs the agent in a worktree
and opens the PRs. It only connects out to buildd, so nothing has to reach in.

## Install

On macOS or Linux:

```bash
curl -fsSL https://buildd.dev/install.sh | bash
buildd login
buildd
```

On Windows (PowerShell):

```powershell
irm buildd.dev/install.ps1 | iex
```

The installer:

- installs [Bun](https://bun.sh) if it is missing
- puts the runner in `~/.buildd` and the `buildd` launcher in `~/.local/bin`
- installs headless Chromium so agents can check their own UI work
- asks whether to run buildd as a background service

It uses `sudo` only when that cannot prompt (you are root, or sudo is
passwordless, and it says so first). Otherwise it skips the step and prints the
command to run yourself. Set `BUILDD_NO_SUDO=1` to skip sudo entirely. For a
scripted install, `curl -fsSL https://buildd.dev/install.sh | bash -s -- --service`
registers the service without asking.

`buildd login` signs you in through the browser and saves an API key to
`~/.buildd/config.json`. It also registers the buildd MCP server in
`~/.claude.json` (skip that with `--no-mcp`). On a machine with no browser, use
`buildd login --device` and approve the code from another device.

`buildd` starts the runner in the foreground. To keep it running after you close
the terminal and across reboots:

```bash
buildd service install   # launchd on macOS, systemd --user on Linux
buildd service status
buildd service logs
buildd service uninstall
```

<Callout type="warn">
  **The runner is headless by default.** It starts an HTTP server only when you
  pass `--debug` or set `PORT`. Without one of those, nothing listens on port
  8766 and `http://localhost:8766` will not connect.
</Callout>

Other ways to give the runner its buildd key:

- **`BUILDD_API_KEY` env var.** Takes priority over the config file. Useful in CI
  and containers.
- **`buildd --debug`.** Starts the debug server on port 8766, which has a sign-in
  route (`/auth/login`) and a `POST /api/config` endpoint.

With no API key, a headless runner prints
`No API key — run with --debug or set BUILDD_API_KEY` and does no work.

The launcher looks for your repos in `~/projects`, `~/dev`, `~/code`, `~/src`,
`~/repos` and `~/work`, and falls back to your home directory. Set
`PROJECTS_ROOT` (comma-separated) to choose. The runner exits at startup if it
cannot resolve at least one project root.

## Model credentials

The runner needs a model credential for the agent it runs. Pick one:

| You have | Set it up |
|---|---|
| A Claude subscription | Run `claude login` on the runner machine, or set `CLAUDE_CODE_OAUTH_TOKEN` in the runner's environment. The seat stays on that machine |
| An Anthropic API key | Store it as a team secret in buildd, or set `ANTHROPIC_API_KEY` on the runner |
| OpenRouter or a LiteLLM gateway | Set an agent model endpoint under **Connections → Model providers**, or set `llmProvider` / `LLM_PROVIDER` on the runner |
| An OpenAI key, for Codex tasks | See [Codex Backend](/docs/getting-started/codex-backend) |

A key or token already in the runner's environment wins over the one buildd
stores. A team agent model endpoint replaces both, and a per-machine
`LLM_PROVIDER` wins over the endpoint. See
[How Buildd Runs AI](/docs/concepts/how-buildd-runs-ai) for the full picture.

## Configuration

All config is stored in `~/.buildd/config.json`. The file path can be overridden
with `BUILDD_CONFIG`, and the containing directory with `BUILDD_HOME`.

### Config Fields

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `apiKey` | string | — | Buildd API key (`bld_xxx`) |
| `serverless` | boolean | `false` | Run without an API key; forced to `false` whenever a key resolves |
| `model` | string | the `standard` tier default | Model to use. Leave it unset to follow your team's tier mapping |
| `maxConcurrent` | number | `3` | Max concurrent workers |
| `acceptRemoteTasks` | boolean | `true` | Accept task assignments from the dashboard |
| `bypassPermissions` | boolean | `false` | Skip permission prompts (dangerous commands still blocked) |
| `openBrowser` | boolean | — | Auto-open browser on startup |
| `builddServer` | string | `https://buildd.dev` | Server URL override |
| `localUiUrl` | string | see [URL Resolution](#url-resolution) | Direct-access URL for this instance, used only in `--debug` mode |
| `pusherKey` | string | — | Pusher key for realtime events |
| `pusherCluster` | string | — | Pusher cluster (e.g. `us2`) |
| `pusherChannelPrefix` | string | `''` | Channel prefix for environment isolation |
| `llmProvider` | string | `anthropic` | LLM provider: `anthropic` or `openrouter` |
| `llmApiKey` | string | — | Provider API key (for OpenRouter, etc.) |
| `llmBaseUrl` | string | — | Custom LLM base URL |
| `maxTurns` | number | — | Max turns per worker session; unset means no limit |

Unrecognised keys in `config.json` are ignored at load time.

### Environment Variables

| Variable | Config field | Which wins |
|----------|--------------|------------|
| `BUILDD_API_KEY` | `apiKey` | **env** |
| `BUILDD_SERVER` | `builddServer` | **env** |
| `MODEL` | `model` | **env** |
| `LLM_PROVIDER` | `llmProvider` | **env** |
| `LLM_API_KEY` | `llmApiKey` | **env** |
| `LLM_BASE_URL` | `llmBaseUrl` | **env** |
| `LOCAL_UI_URL` | `localUiUrl` | **env** (but both lose to headless mode) |
| `PUSHER_KEY` / `NEXT_PUBLIC_PUSHER_KEY` | `pusherKey` | **env** |
| `PUSHER_CLUSTER` / `NEXT_PUBLIC_PUSHER_CLUSTER` | `pusherCluster` | **env** |
| `PUSHER_CHANNEL_PREFIX` | `pusherChannelPrefix` | **env** |
| `MAX_CONCURRENT` | `maxConcurrent` | **config.json** — see below |

<Callout type="warn">
  `MAX_CONCURRENT` is the one exception to "env overrides config". The runner
  resolves it as `config.maxConcurrent || MAX_CONCURRENT || 3`, so **any
  `maxConcurrent` value in `config.json` silently wins** and `MAX_CONCURRENT` is
  ignored. To raise concurrency on a runner that has a config file, edit
  `maxConcurrent` — or remove it from the file first.
</Callout>

Env vars with no config-file equivalent:

| Variable | Effect |
|----------|--------|
| `PROJECTS_ROOT` | Comma-separated project directories (e.g. `~/projects,~/work`). The runner exits if none resolve |
| `PORT` | Listen port (default `8766`) — **setting it at all also enables the HTTP server** |
| `BUILDD_CONFIG` | Config file path (default `~/.buildd/config.json`) |
| `BUILDD_HOME` | Config directory (default `~/.buildd`) |
| `BUILDD_RUNNER_POLL_MIN` | Task-poll cadence in minutes (default `60`) |
| `BUILDD_WORKSPACE_ISOLATION_ROOT` | Opt-in structural workspace isolation root |

Note that every one of these is resolved with `||`, not `??`. A falsy value in
`config.json` — `maxConcurrent: 0`, `builddServer: ""` — falls through to the
next source rather than being honoured.

### CLI Flags

| Flag | Effect |
|------|--------|
| `--debug` | Start the HTTP server and debug UI on `PORT` (default `8766`) |
| `--doctor` | Run diagnostics and exit non-zero on any error |
| `--fix` | With `--doctor`, apply available auto-fixes |
| `--env-verify` (or `env verify`) | Verify the environment |
| `--json` | With `--env-verify`, emit JSON |

There is no argument parser — any other flag is silently ignored.

## URL Resolution

<Callout type="warn">
  This whole ladder applies **only in `--debug` mode**. A headless runner reports
  the sentinel `headless://<hostname>` as its identity and ignores both
  `LOCAL_UI_URL` and `localUiUrl` entirely, so there is nothing for the dashboard
  to link to.
</Callout>

`localUiUrl` determines how the dashboard links back to a debug-mode instance
(the "Open" and "Open Terminal" buttons). It is resolved once at startup:

1. Headless (no `--debug`, no `PORT`) → `headless://<hostname>`, and the steps
   below are never reached
2. `LOCAL_UI_URL` env var
3. `localUiUrl` in `~/.buildd/config.json`
4. Tailscale auto-detect — runs `tailscale ip -4` and uses the IPv4 address
5. `http://localhost:<PORT>` (fallback)

### Remote Workspaces (Coder, SSH, etc.)

To get working dashboard links from a remote machine, run in debug mode and set
the URL explicitly:

```json
// ~/.buildd/config.json on the remote machine
{
  "localUiUrl": "http://<tailscale-ip>:8766"
}
```

Or via env var:

```bash
LOCAL_UI_URL=http://<tailscale-ip>:8766 bun start --debug
```

If the Tailscale CLI is installed on the machine, the IP is auto-detected and you
don't need to set anything — again, only in debug mode.

## How It Works

The runner keeps **two** timers, not one:

| Timer | Interval | Purpose |
|-------|----------|---------|
| Liveness ping | 60 seconds | Pure "runner is alive" signal; drives the online indicator |
| Task-poll cycle | `BUILDD_RUNNER_POLL_MIN` minutes, default **60** | Reconcile local workers, claim-fallback, knowledge ingest |

Both are skipped entirely when `serverless` is set. Extra heartbeats are also
sent at startup, after a claim, and on demand over Pusher.

Server-side, a runner shows as **online** while its last beat is within 1.5× the
task-poll interval, **stale** between 1.5× and 2.5×, and is dropped from runner
queries beyond 2.5×.

1. The runner starts and begins both timers
2. The dashboard shows connected instances under "Connected Agents"
3. When a task is created and assigned, the runner claims it and spawns a Claude Agent SDK session
4. Progress is reported back to buildd.dev in real-time via API + Pusher
5. In `--debug` mode, the dashboard can link directly to the runner for live terminal output
