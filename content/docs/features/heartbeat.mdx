# Heartbeat Monitoring

A **heartbeat** is a recurring check-in on a [mission](/docs/features/missions).
On each tick, Buildd opens a [planning-mode](/docs/features/planning-mode) task
that walks a checklist, decides what the mission needs next, and files the work.
It is the mechanism behind [autonomous operation](/docs/features/autonomous).

Heartbeats are **a property of a mission**, not a separate object. There is no
standalone heartbeat to create and no workspace-level heartbeat setting — you
configure one by setting two fields on a mission.

## Enabling a Heartbeat

```
buildd action=manage_missions params={
  action: "create",
  title: "Keep production healthy",
  workspaceId: "...",
  isHeartbeat: true,
  cronExpression: "*/30 * * * *",
  heartbeatChecklist: "- [ ] API p99 under 200ms\n- [ ] No error-rate spike in the last hour\n- [ ] No certificate expiring within 30 days"
}
```

<Callout type="warn">
`heartbeatChecklist` is a **single string**, not an array. Write it as markdown —
one `- [ ]` item per line, separated by newlines. Passing an array does not give
you a list of items.
</Callout>

Enabling a heartbeat creates a [schedule](/docs/features/schedules) named
`Mission: <title>` whose task template runs in planning mode. If you omit
`cronExpression`, the heartbeat defaults to **every 30 minutes**
(`*/30 * * * *`). The dashboard offers every 30 minutes, hourly, and every 4
hours as presets.

Whether a new mission starts with a heartbeat depends on how it was created:

| Created via | Default |
|---|---|
| Dashboard, with no cron expression and no explicit `isHeartbeat` | Heartbeat **off** — the mission runs a single cycle |
| API or MCP | Heartbeat **on** |

Pass `isHeartbeat: false` to opt out explicitly, which also suppresses the
schedule and the auto-started first cycle.

## The Checklist

If you enable a heartbeat without supplying `heartbeatChecklist`, Buildd
installs a substantial default checklist that drives the mission forward on its
own. It instructs the agent to, among other things: assess which phase the
mission is in; create coding tasks once a plan exists; retry failed tasks with
failure context while leaving cancelled ones alone; retry the originating task
when a PR hits merge conflicts rather than opening a separate integration task;
declare a concrete `pathManifest` on each new task so overlapping work gets
serialized; avoid re-implementing files another task already owns; and refuse to
report OK when the mission has made no forward progress since the last tick.

Supplying your own checklist **replaces** that default, so a short custom
checklist gives up the orchestration guidance along with it. If you only want to
add a check, start from the default and append to it.

The checklist is stored on the mission's schedule template rather than as a
column on the mission, which is why it is read and written through the mission
API rather than a dedicated endpoint.

### Editing the Checklist

From the dashboard, open the mission detail page and edit the **Heartbeat
Checklist** field. Via the API:

```bash
curl -X PATCH https://buildd.dev/api/missions/{id} \
  -H "Authorization: Bearer bld_xxx" \
  -H "Content-Type: application/json" \
  -d '{ "heartbeatChecklist": "- [ ] API health\n- [ ] Error rate\n- [ ] DB connections" }'
```

Or over MCP:

```
buildd action=manage_missions params={
  action: "update",
  missionId: "...",
  heartbeatChecklist: "- [ ] API health\n- [ ] Error rate\n- [ ] DB connections"
}
```

Sending an empty value clears your custom checklist. Reading the mission back
with `action: "get"` shows the active checklist along with whether the heartbeat
is currently running.

## Active Hours

A heartbeat can be confined to part of the day, so an overnight tick doesn't
open work nobody will look at:

```
buildd action=manage_missions params={
  action: "update",
  missionId: "...",
  activeHoursStart: 9,
  activeHoursEnd: 18,
  activeHoursTimezone: "America/New_York"
}
```

Both hours are integers from 0 to 23 and must differ from each other.

## How a Tick Works

1. The schedule fires and materializes its template into a planning-mode task
2. A worker claims it and receives the mission's context and heartbeat checklist
3. The agent works the checklist and returns a structured plan — the follow-up work the mission needs
4. Approving that plan creates the child execution tasks that do the work

Because the task is a planning task, its plan goes through the normal
[plan review](/docs/features/planning-mode) path.

Only **one in-flight planning task per mission** is permitted, enforced by a
database constraint. A tick that arrives while the previous cycle is still
running will not stack up a second one.

When a mission completes, its heartbeat schedule is paused automatically, so a
finished mission stops checking in. See
[Autonomous Operation](/docs/features/autonomous) for how heartbeat cycles are
excluded from a mission's progress percentage.

## Related MCP Parameters

All of these are parameters of `manage_missions` (an **admin-level** action):

| Param | Type | Description |
|-------|------|-------------|
| `isHeartbeat` | boolean | Enable or disable the recurring check-in |
| `heartbeatChecklist` | string | Markdown checklist the agent walks each tick |
| `cronExpression` | string | Tick frequency; defaults to `*/30 * * * *` |
| `activeHoursStart` | number | First hour (0–23) the heartbeat may run |
| `activeHoursEnd` | number | Last hour (0–23) the heartbeat may run |
| `activeHoursTimezone` | string | IANA timezone for the active-hours window |
