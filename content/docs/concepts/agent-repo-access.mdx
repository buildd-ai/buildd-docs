# How Agents Access Your Repo

You authorize buildd once, by installing the buildd GitHub App on your
repository. After that, each agent run gets access of its own. It does not act
as you or borrow your GitHub identity, and it never needs a personal access
token, password or SSH key.

## What you authorize

| Step | Who | What it grants |
|---|---|---|
| Install the GitHub App | A repo or org admin, once | The App's permissions on the repositories you pick |
| Link a workspace to a repo | A team admin, once | Which single repository that workspace's tasks work in |

The repository a task works in always comes from its workspace's link. An agent
can't choose a different one: not through a git remote, the task text, or a
tool parameter.

## What each run gets

When a task runs, buildd mints a GitHub token for **that run only**:

- **One repository.** It's the workspace's linked repo. GitHub refuses the token
  for any other.
- **Short-lived.** It's a GitHub App installation token, which expires within
  an hour. The runner asks for a new one while the run is still going.
- **Only while the run is live.** Once the run ends, fails or is stopped, buildd
  stops issuing tokens for it.
- **Only the permissions a task needs:**

  | Permission | Level |
  |---|---|
  | Contents | write: clone, fetch, push the task branch |
  | Pull requests | write |
  | Issues | write (for comments) |
  | Checks, Actions, Statuses | read (CI state) |
  | Metadata | read |
  | Workflows | not granted |

  It never asks for more than your installation has. Because Workflows is not
  granted, GitHub refuses a push that changes files under `.github/workflows/`.
  Workflow changes go to a person.

## The run's own buildd identity

Each run also gets its own short-lived **buildd** token, so its calls to buildd
(progress, PRs, artifacts, notes) carry the run's identity, not your runner's
key. What that token reaches:

| An agent run can | Only |
|---|---|
| Report progress, finish its task, save artifacts and notes | on its own task |
| Read tasks, PRs, artifacts, runners, schedules, releases, stats and error traces | in its own task's workspace |
| File a follow-up task | in its own workspace, and never into a mission other than its own |
| Edit its task | title, description, priority and links. Status goes through `complete_task`, so the completion checks still run |

Anything team-wide stays with people: workspaces, secrets, schedules, roles,
releases, team settings and other missions. Notes an agent posts are always
marked as written by an agent, never as a person's guidance.

**Organizer, planning and check-in tasks** get the same kind of token at a
higher level. It is still confined to their own mission: they can update that
mission, approve or reject its plans, message its workers and file its tasks,
and nothing outside it.

## Pull requests

PRs are opened through buildd (the `create_pr` action), not with a raw token,
so buildd's rules apply: which base branch a mission's PRs target, how
duplicates are handled, and your workspace's merge policy.

An agent run records, closes or merges only a PR its task owns:

- the PR from its own branch, or from an earlier attempt at the same task;
- a PR the task names ("fix review comments on #42");
- for an organizer, a PR from another task on its own mission.

A PR from one of your protected branches (default or release) is never
recorded as a task's work. Every merge still goes through your merge policy.

## Hosted vs self-hosted runners

| | Hosted runner (preview) | Self-hosted runner |
|---|---|---|
| Where the agent runs | An isolated container per task | Your machine |
| GitHub token | Never enters the container. buildd adds it to the container's GitHub requests on the way out | Written where the agent's `git` and `gh` read it |
| Model credential | Never enters the container | On the runner |
| buildd credential the agent uses | The run's own token | The run's own token, or the runner's key if a token can't be issued |
| Credentials sent by the agent | Removed before the request leaves | Not inspected |
| What the agent can push | Only its own task's branch (or its mission's shared branch), whether by `git push` or GitHub's API | Whatever the token allows. Protect branches with a ruleset |
| Merging through GitHub's merge API | Refused. Merges go through buildd's merge policy | Not refused by buildd |

On a hosted runner, the agent does its work without ever holding a broad
credential. If its container is compromised, there is no GitHub, model or
buildd key inside to steal.

On a self-hosted runner, the agent runs as the same OS user as the runner, so
it can read what that user can read, including the runner's own files. The run
uses its own token for buildd and the runner keeps its key out of the agent's
environment, but only operating-system isolation (the runner's sandbox mode,
or a hosted runner) stops a hostile agent from reading the runner's files. Set
`BUILDD_AGENT_TASK_TOKEN=0` on the runner to have agents use the runner's key
instead, if you need to.

<Callout type="info">
  Whichever runner you use, protect your default branch with a GitHub
  [ruleset](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)
  that requires a pull request. GitHub enforces it on every push, including
  pushes made with the App's token.
</Callout>

## Seeing what a run was given

buildd records every grant and refusal for a run: repo access, buildd tokens,
model endpoints and PR actions. It never records the tokens themselves.

- **Task page, Access:** what that task's runs were given and refused, in
  order, with the reason for each refusal. It opens on its own when something
  was refused.
- **Health, Runners, Agent access:** runs that could not get the access they
  need, with the fix (for example a suspended GitHub App installation or a
  workspace with no linked repo), and what agents were refused, by reason.
- **`explain` on a task:** includes the same history, so an agent or a person
  can ask why something was refused.

Records are kept for 90 days.
