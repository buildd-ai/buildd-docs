# How Buildd Runs AI

Buildd calls models in two places. Each has its own credentials and its own bill.

| | Server-side model call | Runner-side agent run |
|---|---|---|
| Where | The buildd web app | Your runners |
| How long | Seconds | Minutes to hours |
| What it is | One model call, or one streaming chat turn. No repo, no shell | A Claude Code or Codex session with a worktree, tools and commits |
| Used for | Chat, goal-criteria grading, chat's per-turn routing | Every task: building, research, planning, PRs |
| Paid with | A provider **API key** (Anthropic, OpenAI, OpenRouter) | A **subscription** (Claude or ChatGPT/Codex) or an API key |
| Billed | Per token | Per seat, or per token if the runner uses an API key |

<Callout type="info">
  A subscription can't pay for server-side calls. Subscription login is tied to
  the runner that holds it, and a single server request has no seat to use. So
  server-side features always need an API key, and a runner never uses those
  keys.
</Callout>

## Server-side model calls

These run inside buildd and return in seconds.

| Feature | Setting | With it off |
|---|---|---|
| Chat | On once a key resolves. An admin can turn it off | No chat. The mission form works as before |
| Goal criteria grading | Off until an admin turns it on | An agent run on your runner grades written criteria instead, slower and on its seat |
| Task category shadow check | Off until turned on | Nothing. It only logs whether a model agrees with the keyword rules |
| Visual QA judgment, task classification, mission summaries | Listed in **Settings → AI features** | No buildd feature calls these yet. Turning them on spends nothing |

Two rules apply to all of them:

- **Storing a key spends nothing.** Apart from chat, each feature is off until an
  admin turns it on in **Settings → AI features**.
- **Chat never falls back to a runner or a subscription.** With no key, the chat
  box becomes the mission form and explains what's missing.

Providers per feature:

| Path | Anthropic | OpenAI | OpenRouter |
|---|---|---|---|
| Chat | Yes | Yes | Yes |
| Grading and other one-shot calls | Yes | No | Yes |

A chat tier mapped to an Anthropic or OpenAI model still works with only an
OpenRouter key. Buildd serves the same model through OpenRouter.

### Chat budgets

Chat is capped by default. There is no "no cap" setting.

| Limit | Default | Where |
|---|---|---|
| Team daily chat budget | $20, reset at midnight in the team's timezone | **Settings → Budgets** |
| Per-person daily share | Half the team budget | **Settings → Budgets** |
| Turn rate | 30 turns per person per 10 minutes | Fixed |

A team budget of `0` pauses chat. Chat spend is tracked apart from runner
spend and never counts against an account's `maxCostPerDay`.

## Runner-side agent runs

Runners do the actual work: they clone the repo, run the agent harness, and
open PRs. Credentials for them are covered in [Secrets & Credentials](/docs/concepts/secrets)
and [Codex Backend](/docs/getting-started/codex-backend).

| Harness | Subscription | API key |
|---|---|---|
| Claude Code | Claude OAuth token (`oauth_token`) or Claude credentials (`claude_credential`) | `anthropic_api_key` |
| Codex | ChatGPT/Codex `auth.json` (`codex_credential`) | `OPENAI_API_KEY` on the runner |
| Claude Code via OpenRouter | — | `llmProvider: openrouter` + `llmApiKey` in the runner's config |

Credentials on the runner itself win. Server-managed secrets are the fallback,
delivered when a runner claims a task.

**Why the runner still matters when you pay per token:** Serverless hosts
can't hold a process for an hour, and agent work needs a real filesystem and
shell. The runner is where that runs, whoever pays.

**Why a subscription is usually cheaper for agent work:** a long agent run can
use millions of tokens. On a seat that costs nothing extra until you hit the
plan's usage window. The cost buildd shows for seat runs is an estimate
(labelled virtual), not money spent.

## Keys: the team's or each person's

Server-side keys are managed in **Settings → Model providers**. Connect
OpenRouter with one click, or paste an Anthropic, OpenAI or OpenRouter key. Only
the last four characters are shown after saving.

An admin picks one policy for whose key a person's chat turns spend:

| Policy | Who pays for chat | A person's own key |
|---|---|---|
| Team key (default) | The team key, for everyone | Ignored |
| Team key, own key allowed | A person's own key if they added one, else the team key | Optional |
| Everyone brings their own | Each person's own key | Required. No team key fallback |

Members add their own key under **Settings → Account**. A personal key only ever
pays for its owner's turns.

<Callout type="info">
  The policy only covers chat, because chat runs for a person. Grading and other
  team work with no person behind it use the workspace key, then the team key,
  whatever the policy says.
</Callout>

## Model tiers

Nobody picks a vendor model per task or per chat. Callers ask for a **tier**; an
admin decides which model backs it.

| Tier | Meant for |
|---|---|
| `premium-plus` | Opt-in only. Nothing is routed here unless a task or role asks for it |
| `premium` | Planning, hard engineering, design |
| `standard` | Most engineering and research. The default |
| `budget` | Fast, cheap calls: triage, classification |

Admins map each tier to a provider and model in **Settings → Model tiers**
(or the `manage_model_tiers` MCP action), for the whole team or one workspace.
Buildd resolves a tier in this order:

1. The workspace's mapping
2. The team's mapping
3. The newest model in the tier's price band from the live model catalog
4. Built-in defaults

Things to know:

- **Agent runs resolve at claim time.** Change a mapping and tasks already in the
  queue pick up the new model. Changes apply within about a minute.
- **An explicit `model` wins.** A task with `model` set, or a role pinned to a
  full model ID, skips tiers entirely.
- **Chat picks a tier per turn.** A quick classifier sends simple turns to
  `budget` and complex ones to `premium`. When it's unsure, or unavailable, the
  turn uses `standard`. It never changes which model backs a tier.

<Callout type="info">
  **Tier model pools** — several models behind one tier, with traffic split and
  graded between them — are designed but not shipped. Today each tier maps to
  one model.
</Callout>

## What to set up

| You... | Runners | Server-side | Key policy |
|---|---|---|---|
| **Pay per token** | Store an `anthropic_api_key` secret, or set `OPENAI_API_KEY` on the runner for Codex. Runners still run the agent | Add an OpenRouter, Anthropic or OpenAI key in **Model providers**. Turn on goal grading in **AI features** if you want grading in seconds | Team key |
| **Have a Claude or ChatGPT subscription** | Add the Claude OAuth token or Codex `auth.json`. This is where the heavy work runs | Optional. Add an API key only if you want chat or fast grading. Leave grading off to keep it on your seat | Team key, or let people bring their own |
| **Self-host** | Same as either row above | Either add keys in the app, or set `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / `OPENROUTER_API_KEY` **and** `BUILDD_ALLOW_ENV_INFERENCE_KEYS=1` | Any |

<Callout type="warn">
  In production, provider env vars are ignored unless
  `BUILDD_ALLOW_ENV_INFERENCE_KEYS=1` is set. Without it, a self-hosted deploy
  with only `ANTHROPIC_API_KEY` in its environment has no server-side key, and
  chat stays off. Env keys are also a last resort: any
  key stored in the app wins, and under the "everyone brings their own" policy
  chat never reads them.
</Callout>
